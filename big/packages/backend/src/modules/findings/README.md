# findings/

Normalize, store, and query scan findings.

> **Scanner v1 status:** this module is scaffolding for v2. The current scanner
> flow does not ingest findings into CP — scanners host their own report
> dashboards and CP redirects users there. The module remains in place so the
> table shape and ingest API are ready when v2 brings findings into CP.

## Flow diagram coverage

- GU — findings generated by scanner (happens outside our system; ingest via callback)
- K1 — normalize results to common schema
- L1 — tag with org_id, scanner_type, run_id, timestamps
- M1 — store findings in DB
- N1A — store raw artifacts / evidence
- R1 — dashboard shows latest run status (read from here)
- S1 — dashboard shows findings summary (read from here)
- T1 — user opens scan details
- U1 — backend fetches only org-scoped results (enforced by `orgId` filter everywhere)
- V1 — user sees findings, evidence, severity, recommendations

## Responsibility

Canonical home for scan results. Owns the `Finding` model + `ScanArtifact` (shared with `scanner-callbacks`). The normalizer maps scanner-specific output shapes to a single DB schema.

## Public API

| Method | Path | Role | Description |
|---|---|---|---|
| GET | `/findings` | any member | List findings for current org, filter by `scanJobId`, `severity`, `status`, `scannerKey` |
| GET | `/findings/:id` | any member | Finding detail with evidence + recommendation |
| PATCH | `/findings/:id/status` | `org_admin` \| `org_member` | Triage: OPEN → TRIAGED / ACCEPTED / RESOLVED / FALSE_POSITIVE |

## Normalization schema

Every scanner's output is mapped to:

```ts
{
  externalId?: string,      // scanner's own id for this finding
  title: string,
  description?: string,
  severity: INFO | LOW | MEDIUM | HIGH | CRITICAL,
  resource?: string,        // which asset/target (e.g. "s3://bucket/key")
  evidence?: object,        // scanner-specific detail (JSON — store as-is)
  recommendation?: string,
  tags: string[],
}
```

`evidence` is the freeform-but-typed-by-scanner field. Don't try to flatten it — just store the scanner's JSON. The detail view will render it scanner-aware in the frontend.

## Idempotency

`ingestFromCallback` may be invoked twice for the same job (retry, double-callback). Dedupe key: `(scanJobId, externalId)` if externalId present, else `(scanJobId, title, resource)`. Use an upsert pattern or a "has this job been ingested?" marker on the `ScanJob` row.
